## [0:00 — 1:30] 开场

好，我们开始第六课。

上节课我们用 OpenSpec 解决了**"做什么"**——把一个 feature 的需求结构化成 proposal、specs、design、tasks、IMPLEMENTATION 五份磁盘文件。当时讲过一句话：**spec 是 AI 与你之间的合同**。

OpenSpec 其实已经悄悄解决了一件事——**跨会话续接**。tasks.md 里那些 `- [ ]` checkbox 写在磁盘上，今天 implement 到一半，明天重启 Claude Code，新会话读 tasks.md 看哪行还是 `[ ]`、从那里接着干。**这就是把任务状态从"AI 的记忆"搬到"磁盘文件"的雏形**。lesson 5 没明说，但这种"用 markdown 文件作为 AI 跨会话外脑"的思路，是 OpenSpec 能 work 的真正机理。

今天我们把这个思路**拎出来、显式化、推广到一切长任务**——这个更通用的工程模式就叫 **harness**。OpenSpec 是 harness 的一种特化形态（**只**针对 spec-driven feature，**五段固定**，**只管"做什么"**）；今天讲的 Superpowers 风格 harness 是更通用的形态——**任意长任务**都能套：跑回测、做数据分析、批量重构、写文档……都能用同一套 plan + HANDOFF 文件管。

打个比方：**OpenSpec 是一辆给 feature 量身定做的轿车，harness 是底盘**——你可以在底盘上造轿车、卡车、皮卡，OpenSpec 是其中一款。今天我们讲底盘怎么造。

具体怎么演示？用 `superpowers` 插件——这是 obra（Jesse Vincent）做的第三方开源插件、托管在 Claude 插件市场，**不是 Anthropic 官方的**，但因为质量高、被广泛采用，社区里讲 harness 默认就用它当标杆。我们重点用它里面两个 skill：`writing-plans` 和 `executing-plans`——配一个真实的多周期回测任务，**课堂上跑一次 `/clear` 再续上**，让大家亲眼看到上下文断了、任务没断。

今天四块：Harness 是什么、Harness 的四要素、Superpowers 14 个 skill 速览、演示。

先确认环境——讲义 §〇 前置确认，5 件事都打钩了我们就继续。

## [1:30 — 4:30] §一 Harness 是什么（3 分钟）

好，第一块。

我先问大家一个问题：你们有没有遇到过这种情况——让 Claude 做一个 10 步的任务，前 6 步漂亮通过，到第 7 步它开始问"我们刚刚改的是哪个文件来着"。

我自己第一次见到这种情况是去年做一个大重构，让 Claude 重构 8 个文件，跑到第 6 个的时候它开始把第 3 个文件的接口写错——后来我才意识到，上下文窗口已经塞了 70k tokens，模型记忆开始衰退。**Claude 不会自动 /clear，但它会"变笨"**——这是一个隐蔽得多的失败模式。

这种"变笨"的根本原因是：**模型本身没有持久记忆**。当前会话的所有 state——你刚刚跑过哪个命令、得到了什么数字、做出了什么决定——全部活在上下文窗口里。窗口满了，或者你 `/clear`，state 就丢了。这不是 bug，是大模型的天然限制。

那怎么办？

我给大家一个生活化的类比，理解 harness 一下就通了。**Harness 就像工地的施工日志本**——工人下班、第二天换班、下个月甚至换一家施工队，只要日志本一直留在工地上，下一拨人翻开日志就知道"昨天干到第 5 层、今天该浇第 6 层混凝土"。AI 也一样——`/clear` 相当于下班，重开 Claude Code 相当于换班。只要进度都写在日志（也就是 plan 文件）里，**任务永远不会"断"**。

Harness 的核心思想就一句话：**把 state 从上下文里搬到文件里**。

你跑了一个命令拿到一个数字——不要"记在心里"，写到一个 markdown 文件里。下一步要做什么——也不要"知道就行"，写到那个 markdown 文件里。这样 AI 的上下文变成什么？变成**工作台**——可以随便清，因为真正的进度都在磁盘上。

讲义里有一张对比表，我把它念出来：

| | vibe 会话 | harness 会话 |
|---|---|---|
| 进度记在哪 | AI 的上下文里 | plan 文件里 |
| /clear 后会发生什么 | 一切重来 | 读 plan 接着干 |
| 任务上限 | 一个上下文窗口 | 无上限 |
| 跨会话/跨人协作 | 不行 | 把 plan 路径给下一个人就行 |

最后一行是 harness 的真正杀手锏——**跨人协作**。如果你的进度都在一个 markdown 文件里，那今天我做一半，明天换一个人接着做，完全可以——他读那份 plan 就行。**这是 AI 时代的 git commit message**——人类不再需要"跟踪 AI 在干什么"，AI 自己把状态写下来。

记住一句话：**Harness 把任务从 AI 的"记忆"里拿出来，放进可审计、可移交、可断点续跑的文件**。

回到开场那个 OpenSpec 的事补一句：上节课你们在 OpenSpec `tasks.md` 里勾 `[x]` 那个动作——其实就是 harness 在做的事，只是 OpenSpec 把它包在了"5 段 spec 流程"里、绑定了"做 feature"这一个场景。本课讲的 plan 文件是同一类东西，只是**模板更通用**——任何"多步长任务"都能套，不限 feature。所以这两节课不是矛盾，是从特例（OpenSpec）走到通例（harness）。

## [4:30 — 7:30] §二 Harness 的四要素（3 分钟）

来看 harness 怎么实现。讲义里有一张表，四个动作：

**第一个：init**。把一个任务展开成 plan 文件——拆 step、画 scenario 表、写 Goal 和 Architecture。这一步是脑力工作，一次性的——任务开始前花 10 分钟把 plan 写好，后面省心一周。Plan 文件落到 `plans/<task-name>.md`。

**第二个：execute**。按 plan 一步一步跑，每跑完一步就**回填到 plan 里**——把数字填到表里，把 `[ ]` 改成 `[x]`。这一步是肌肉记忆——每个 step 都包含"跑命令 + 看输出 + 改 plan"三个动作，缺一不可。

**第三个：checkpoint**。跑一段之后写一份交接快照——把当前进度、关键中间结果、下一步要做什么写到 `HANDOFF.md`。这一步看似多余——plan 里不已经有进度了吗？但是 HANDOFF 解决一个更细的问题：**下一个会话第一句话该说什么**。

**第四个：handoff**。在 HANDOFF.md 里写一段**可整段粘贴的 prompt**——下一个会话只要把它粘进对话框，AI 就知道从哪续。

我重点说一下 init 和 execute 之间的关系。很多人写 plan 写得很认真，但 execute 的时候偷懒——跑完一步只是"心里知道做完了"，没去改 plan。这是 harness 最常见的死亡模式。

**Plan 不是写完一次就放那的——plan 是边跑边改的**。你跑了一次回测，立刻回填数字、立刻打勾——这两件事都做完，这一步才算完成。光跑不写，那 plan 就成了化石；化石是没用的，化石让下一个会话以为"还没人跑过"。

三件套：plan、HANDOFF、report。Plan 是过程记录，HANDOFF 是会话交接点的快照，report 是最终聚合的结论——这三个文件落到 `plans/`、`plans/HANDOFF.md`、`reports/` 三个位置。

最后一句话：**Harness 不是工具，是约定**。

## [7:30 — 10:30] §三 Superpowers 的 14 个 skill 速览（3 分钟）

讲约定有点空，我们来看社区怎么把这套约定打包成一组 skill——`superpowers` 插件，作者是 obra（Jesse Vincent），托管在 Claude 插件市场。这个插件 lesson 2 已经装过，今天我把它**整套** 14 个 skill 都过一遍——你不用记，看讲义里那张表就行，我口播的是**它们怎么分组、各自管什么**。

我把 14 个 skill 分成 5 组：

**第一组：计划与执行**——也就是今天 demo 的主角，三件套：
- `writing-plans`：把一个多步任务展开成 plan 文件，含 Goal / Architecture / 进度表 / Tasks / Resume Protocol——任何"有 spec、要落地多步"的工作起点。
- `executing-plans`：读一份现成 plan、按 step 跑、跑完一步立刻回填一笔——今天我们演示用的就是这个。
- `subagent-driven-development`：每个 task 派一个新 subagent 去跑，跑完两段 review——适合 plan 里任务彼此独立、可以并行的场景。

**第二组：思考与设计**——AI 干活之前的脑子先用对：
- `brainstorming`：用对话式问答把"我想做 X"磨成可写 spec 的设计。
- `writing-skills`：用 TDD 的方式写新 skill——把你自己的高频流程沉淀成 SKILL.md。这是个元 skill：写 skill 的 skill。

**第三组：实现纪律**——AI 写代码过程中守底线的三个：
- `test-driven-development`：先写测试看它挂、再写最少代码让它过。
- `systematic-debugging`：遇到 bug 必须找根因再动手，禁止"哪里报错就改哪里"。
- `verification-before-completion`：声称"完成"之前必须真跑一遍验证命令——证据先于断言。

**第四组：评审与协作**——多 AI / 多人协作的三个：
- `requesting-code-review`：派一个 code-reviewer subagent 看本次 diff——这是 lesson 7 verify.sh 的第 3 节点。
- `receiving-code-review`：收到 review 意见时先技术核实，不机械执行也不顶嘴。
- `dispatching-parallel-agents`：把 2+ 个相互独立的任务派给不同 subagent 并行跑。

**第五组：环境与收尾**：
- `using-git-worktrees`：起一段独立 feature 之前先 worktree 隔离工作区——不打扰当前分支。
- `finishing-a-development-branch`：实现+测试都过了之后，告诉你接下来该 merge / PR / 清理。
- `using-superpowers`：插件自己的元 skill——告诉 AI 怎么找/用其它 skill。每段会话开头自动调起。

14 个 skill 加起来，覆盖了一个 AI 写代码会经历的**全部阶段**——从想清楚要做什么，到写计划、跑、调试、review、收尾。今天我们演示的只是其中两个——但你课后写自己项目的时候，这 14 个里至少有 6-7 个都能用上。讲义最后的延伸阅读里有这 14 个 SKILL.md 的本地路径，每一份都不到 5 分钟能读完。

**关键认知**：这 14 个 skill 里**一行代码都没有**——全是 prompt 工程。它们解决的不是"AI 不会做某件事"，而是"AI 没人告诉它应该按什么纪律做"。Vibe coding 的失败不是因为模型不聪明，而是因为模型不知道"跑完一步要回填"、"声称完成前要验证"、"遇到 bug 要找根因"。Superpowers 干的就是**把这些纪律显式化**——让 AI 默认按这些方式工作。

今天演示用 `writing-plans` + `executing-plans` 两个，因为它们和 harness 的关系最直接。

## §五 + §六 关键认知 + 反模式（2.5 分钟）

讲义 §五 关键认知那一段写得已经很清楚，我补充一个往后看的视角。

讲义里有一个口诀，我念一下：

```
state 不在脑子里，state 在 plan 里
跑一步，回一笔
HANDOFF 写得越具体，下一个会话越省心
```

我重点说第二条——"跑一步，回一笔"。这一条是 harness 整个体系里**唯一一条不允许妥协**的纪律。其他的——plan 写得多详细、HANDOFF 用什么格式——都可以根据任务调整，唯独这一条不行。

为什么？因为 harness 的全部价值都建立在"plan 文件 = 真实进度"这个等式上。一旦你某一步偷懒不回填，这个等式就破了——后面任何一次续接都会出错，下一个 AI 读到一份不准确的 plan，会以为"还没跑过"，于是重复劳动。**不维护的 plan 比没有 plan 还有害**——它给人虚假的确定性。

讲义 §六 三个反模式我快速过一下，每个我说一个真实场景。

**第一个：Plan 写完不维护**。我自己见过最严重的一次是一个学员跑 backtest，跑了 8 个 scenario，全部跑完才一起改 plan。结果第 5 个跑的时候断网了，AI 重启会话之后，前 4 个数字它说"我记得是这样这样"——具体是哪 4 个数字，记不清了。整个上午白干。**所以——跑一次回填一次，没有例外**。

**第二个：Plan 太抽象，每个 step 都需要解释才能跑**。最常见的反例是"Step 1: 把回测跑起来"。这是空话——"跑起来"是什么命令？跑完看什么算完？AI 看到这种 step，第一反应是回头问"具体怎么跑"，然后你又要花 30 秒回答——还不如一开始就把命令写到 plan 里。Plan 要**自包含**到不需要额外说明的程度。

**第三个：HANDOFF 不指向具体下一步**。"进度：Phase 1 跑完了，准备 Phase 2"——这种 HANDOFF 等于没写。下一个会话看到"准备 Phase 2"还要回头问"Phase 2 是什么、怎么开始"。HANDOFF 的全部意义就是**让下一个会话不需要思考**——里面必须有一段直接可粘贴的 prompt，整段粘进去就能开工。

## §七 作业 + 收束（2 分钟）

作业之前先回答一个你们一定会问的问题：**"我没有长任务可练怎么办？"**

不需要长任务——你随便挑一个 3-5 step 能完成的真实工作就行。讲义里给了三个候选：把仓库 README 翻译成英文、把 lesson 4 backtest 跑更多策略、把一个长函数拆成 4 个小函数。任何一个都够练 harness 纪律。

作业一件事：**写一份 mini plan，跑过一次真的 `/clear` 续接**。

主要工作是**练 harness 的纪律**——写 plan、回填、HANDOFF、续接——不是练任务长度。30 分钟内可以完成。作业说明在 `lesson6/homework/task1-harness/README.md`，里面有 `PLAN.md.template`，你复制下来按格式填。

提交两样东西：最终版 PLAN.md（全部 `[x]`），加一段 200 字感受——续上的体验如何？plan 写到多详细才够？

最后说一句：学完这节课，你能解释 harness 是什么、为什么 AI 需要它、四要素分别落到哪个文件，能用 superpowers 风格写一份可续跑的 plan，跑一遍 "Phase 1 → /clear → Phase 2" 的完整流程。

Lesson 7 我们处理另一个问题——**harness 跑得起来，但怎么保证别人改了代码不会把它跑挂？** 答案是 CI——把"每次都人工跑一遍 verify"升级成"在仓库里钉一道闸门，任何提交都自动跑、不过就 block"。Lesson 6 教 plan 怎么写得让 AI 能续，lesson 7 教 verify 怎么写得让 CI 能挡——一前一后，是 AI 时代工程纪律的两端。
