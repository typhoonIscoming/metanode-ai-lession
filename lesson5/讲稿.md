## [0:00 — 1:30] 开场

好，我们开始第五课。

上节课我们造了一个接口——把"策略回测"封装成 backtest Skill，让 Claude 日后只需要听到"帮我回测"就能调用完整的流程，不需要每次重新解释 `run_backtest` 怎么用、签名是什么、返回值怎么解读。那节课的核心是"能力沉淀"：把可复用的流程沉淀到 SKILL.md，让 Claude 按图索骥。

今天我们把视角往前推一步，看**需求那一侧**。

能力沉淀解决了"怎么做"的问题，但在"怎么做"之前，还有一个更基础的问题没有解决——**你到底要做什么，有没有说清楚？**

Vibe coding 失败的根本原因不是 AI 不够聪明。AI 很聪明，聪明到它会根据概率猜你的意思，然后给你一个看起来"完全正确"的实现——直到你上了生产，才发现它猜错了一个关键细节，而那个细节你从来没有明确说过。

今天要解决的就是这个：用 OpenSpec 五段流程，在动手写代码之前，先写一份结构化的变更文档，把"要做什么"说得足够清楚，让实现阶段只负责落地——不靠猜，不靠运气。

## [1:30 — 4:00] §一 vibe coding vs spec-driven（2.5 分钟）

进入第一块，先聊一个真实失败案例。

我去年让 AI 帮我给量化系统加一个双均线策略，需求说得我觉得挺清楚的："金叉买入、死叉卖出，短均线 7 日，长均线 14 日"。AI 三分钟给了一个 Python 文件，能跑、不报错、有中文注释、逻辑看起来完全对。我跑了一遍回测——夏普 4.0+，累计收益超过 30%，太美好了。

然后我仔细看了代码，发现问题了。

它用的均线是这么计算的：

```python
# vibe coding 产物（AI 猜的，有 lookahead）
ma_short = df["close"].rolling(7).mean()     # ❌ 今天的信号用了今天的 close
signal = (ma_short > df["close"].rolling(14).mean()).astype(int)
```

注意这里——`rolling(7).mean()` 是用包含今日 close 在内的 7 天均线，然后当天就根据这个均线开仓了。问题在哪？**今天的收盘价，今天收盘之前你根本不知道**。这叫 lookahead bias，又叫未来数据偷看。历史回测看着漂亮，是因为它在用"作弊"的数据——用了当天才能知道的信息来做当天的交易决策，实盘一塌糊涂。如果上线，第一天就会爆雷。

另外，`short_window=3, long_window=5` 这两个参数是 AI 随手给的，没有任何文档支撑"为什么是 3 和 5"，三个月后的你完全猜不出当时的依据。

这就是 vibe coding 的真实代价——不是 AI 水平不够，是需求本身就是模糊的，AI 凭概率猜，猜对了是运气，猜错了你不一定立刻发现。

**同样的需求，spec-driven 怎么做？**

你先写一份 `specs.md`，在里面写清楚："均线用 `df["close"].shift(1).rolling(N).mean()` 计算，`shift(1)` 确保信号决定时不读今日 close"；"默认 `short_window=7, long_window=14`"；"金叉给信号 `+1`，死叉给 `0`，其他维持上一日"。

```python
# spec-driven 产物（合同里写了 shift(1)）
ma_short = df["close"].shift(1).rolling(7).mean()   # ✅ 只读昨日及以前
ma_long  = df["close"].shift(1).rolling(14).mean()
```

AI 拿到这份合同，实现就只是把这些约定翻译成代码。lookahead 防护不是"看 AI 高不高兴"，而是合同上写了的，AI 不实现就是违约。这两段代码历史回测的夏普可能差距超过 2 倍，spec 让这个差距变成**可审计**的——任何人打开 `specs.md` 都能验证实现里有没有 `shift(1)`。

**一句话总结：spec 是 AI 与你之间的合同——没有合同就只能赌运气。**

## [4:00 — 6:00] §二 rules / guidelines / spec 三者（2 分钟）

好，第二块。规则体系不是只有一层，是三层叠加：rules、guidelines、spec。

讲义里有一张对比表，我念一下：

| 层 | 例子 | 强制度 | 维护成本 |
|---|---|---|---|
| rules | UTC 时间 / 中文注释 | 高，违反 = 失败 | 低，很少改 |
| guidelines | 函数命名风格 | 中，违反 = 风格不一致 | 中 |
| spec | dual_ma 接口签名 + 行为细则 | 中，违反 = 合同纠纷 | 高，每个 feature 一份 |

三者各司其职，不是互相替代的。

**Rules 是底线**——全项目必须满足的硬约束，比如"所有时间必须用 UTC"、"所有注释必须写中文"。这类约束写进 `.cursor/rules/strategy-conventions.mdc` 之后，Claude 每次编辑 `strategies/*.py` 文件时都会自动读到，不需要你在每条 prompt 里重复说。你只需要说一次，它就永远有效。

**Guidelines 是味道**——让代码看起来像一家人写的。函数命名用动词_宾语、目录结构约定、日志格式——这些不影响正确性，但影响可维护性。违反了代码能跑，但读着别扭，团队维护的时候会有沟通成本。

**Spec 是合同**——描述具体 feature 的接口是什么、边界条件是什么、不支持什么。只对这一个 feature 有效，feature 交付后归档，不需要持续维护。

三层协作的逻辑：rules 划底线，guidelines 划风格，spec 描述具体 feature。三层叠加，AI 才能稳定输出，不靠猜——不是只有一层 spec 就够了。

本课里，rules 落地在 `.cursor/rules/strategy-conventions.mdc`，可以运行 `cat .cursor/rules/strategy-conventions.mdc` 看一下内容，感受它和 spec 的区别。Rules 是"设一次用永远"；spec 是"每个 feature 写一份用一次"。（注意：rules 文件在仓库根 `.cursor/rules/`，各 lesson 快照不单独带一份。）

## [6:00 — 9:00] §三 OpenSpec 五段速览（3 分钟）

第三块，OpenSpec。

OpenSpec 把每个 feature 的"变更过程"拆成 5 个 markdown 文件，放在 `lesson5/project/openspec/changes/<change-id>/` 下：

| 段 | 文件名 | 干啥 | 关键问题 |
|---|---|---|---|
| ① | `proposal.md` | 提案 | 现状有什么问题？要做什么？ |
| ② | `specs.md` | 规范 | 接口怎么定义？边界条件？ |
| ③ | `design.md` | 设计 | 备选方案对比，关键技术决策 |
| ④ | `tasks.md` | 任务 | 拆成 5-10 步可执行清单 |
| ⑤ | `IMPLEMENTATION.md` | 实施记录 | 落地代码 + 与 design 的偏差 |

我想在这里说一个很重要的认知：**这五段不是凭空发明的工具，是把"加新功能"这件事本来就需要思考的五个问题，拆出来，各自给一个文件。**

你加任何一个新功能，都绕不过这五个问题：为什么要做？接口是什么？为什么这么设计？分几步做？做完记录什么？只不过在 vibe coding 模式下，你把这五个问题的答案藏在脑子里，AI 只从你的一句话 prompt 去猜。OpenSpec 的作用就是把这五个答案**显式地写出来**，让 AI 有合同可依，不靠猜。

每一段都对应一个**可以问的问题**：

- proposal 的问题是：你为什么要加这个东西？
- specs 的问题是：接口签名是什么？边界情况怎么处理？
- design 的问题是：你考虑过哪些方案，为什么选了这个？
- tasks 的问题是：分几步做，每步的动作是什么？
- implement 的问题是：最终落地是什么样，和 design 有什么偏差？

关于工具，我口播一遍讲义 §〇 写的内容，因为这一段最容易被跳过：**OpenSpec CLI 是可选的便利层**。这套约定本身是纯文件驱动的，`openspec/` 目录里的 markdown 就是全部——你完全可以手写五段，不依赖 CLI。但如果想用 `/opsx:propose` 这类 slash command 把"敲五个文件"压缩成一行，那就装一下 CLI：`npm install -g openspec` + 在 `lesson5/project/` 下跑 `openspec init`，会自动落 `openspec/config.yaml` 和 `.claude/commands/opsx/*`、`.claude/skills/openspec-*/` 这几样东西。本课的样本 `add-dual-ma-strategy` 两种方式产出的结构完全一致——如果你跟着课程仓库走，这一步其实已经做过了，你直接用 slash command 就行。我自己之前讲这一段时说过"不需要安装 CLI"，那个说法其实是误导——准确的说法是"CLI 是可选的"，因为方法论本身不依赖工具，但工具能省力。

```bash

```

期望看到：`proposal.md  specs.md  design.md  tasks.md  IMPLEMENTATION.md`，五段全齐。

## [9:00 — 12:00] §四.1 + §四.2 proposal + specs（3 分钟）

进入动手做环节，跟着 `add-dual-ma-strategy` 这个 change，走一遍五段全流程。

**先看 proposal.md：**

```bash
cat lesson5/project/openspec/changes/add-dual-ma-strategy/proposal.md
```

5 行核心：

> lesson 4 backtest skill 已就绪，但 `lesson5/project/strategies/` 里只有 buy_and_hold / ma_crossover_7 两个 example。buy_and_hold 是基线，没有交易决策；ma_crossover_7 是单条均线突破，没有"反转信号"。**提案**：实现双均线交叉策略 `dual_ma`——短均线（7 日）上穿长均线（14 日）给信号 `+1`（做多），下穿给信号 `0`（空仓），其他维持上一日。

注意 proposal 不写代码细节，只写三件事：**现状缺什么、要解决什么、怎么算完**。一个好的 proposal，30 秒内读完就能抓到痛点，不需要背景知识。

文件里还有"影响范围"和"验收"两段——影响范围告诉协作者"会动哪些文件"，让做代码审查的人知道往哪看；验收告诉 AI"怎么判断做完了"，防止 AI 觉得"写完代码就算完"，忘了跑自测、忘了更新文档。

**再看 specs.md：**

```bash
cat lesson5/project/openspec/changes/add-dual-ma-strategy/specs.md
```

接口段：

```
dual_ma(df: pd.DataFrame, short_window: int = 7, long_window: int = 14) -> pd.Series
值 ∈ {0, +1}（不做空）
```

信号规则表：

| 状态 | 当日信号 |
|---|---|
| 金叉（短上穿长：`ma_s > ma_l` 且昨日 `ma_s ≤ ma_l`） | `+1` |
| 死叉（短下穿长：`ma_s < ma_l` 且昨日 `ma_s ≥ ma_l`） | `0` |
| 其他（持仓维持） | 与昨日信号相同 |

防 lookahead：均线用 `df["close"].shift(1).rolling(N).mean()` 计算，只读昨日及以前。

我重点讲这一张状态表。**为什么 specs 必须有状态表？因为这是合同——合同上的每一条都必须明确。** "ma_s > ma_l 时该返回什么"必须是白纸黑字，不能是"AI 你看着办"。模糊就给 bug 留了空间：如果只写"金叉买入"，AI 可能理解为 `ma_s >= ma_l` 就是金叉，漏掉了"昨日状态"这个条件，结果是横盘时每天都在反复开仓平仓，信号完全乱掉。

还注意文件里有"不支持"段：明确写出"做空返回 -1 不支持"。这和"支持 +1"一样重要——告诉 AI 哪些**不做**，防止 AI 过度实现（auto-generalize），加了一堆你不需要的功能，比如自动加入做空逻辑，反而引入了没经过验证的行为。

## [12:00 — 15:30] §四.3 + §四.4 design + tasks（3.5 分钟）

**看 design.md：**

```bash
cat lesson5/project/openspec/changes/add-dual-ma-strategy/design.md
```

备选方案对比：

| 方案 | 实现复杂度 | 教学清晰度 | 选择 |
|---|---|---|---|
| A. close vs MA（简单突破） | 低 | 高，但和 lesson 4 ma_crossover_7 雷同 | ❌ |
| B. 短 MA vs 长 MA（金叉死叉，本提案） | 中 | 高，经典量化教科书例 | ✅ |
| C. MACD（DIF/DEA） | 高 | 高，但额外引入 EMA 概念，超出 25 min | ❌ |

design 这一段，我重点讲**两层防御 lookahead**这个决策，因为这是真实工程经验，不是随便加的。

两层防御是这样的：策略层用 `df["close"].shift(1).rolling(N).mean()` 计算均线——把价格数据往前移一格，所以今天看到的均线，是截至昨天的 N 日平均；然后 `backtest.py` 里还有另一个 `signal.shift(1)`——把信号再往后移一格，今天执行昨天决定的信号。两层防御，确保不读未来数据。

为什么要两层，不是一层就够了？因为**一层防御容易被绕过**。具体来说：假如策略层忘了写 `shift(1)`，直接用了今日收盘均线，这时候 backtest 层的 `signal.shift(1)` 只能防止"用今天信号执行今天交易"，但它没有能力发现策略层已经偷看了今日收盘价。两个 `shift(1)` 各司其职，策略层的那个保证"均线计算不看今日"，backtest 层的那个保证"执行不超前"，缺任何一层都有漏洞。这是两层冗余设计，比只依赖一层更稳。

三个月后你再回来看这份 design，不需要猜"当时为啥两个 shift"——因为 design 里写了答案。这就是 design 文件的核心价值：记录"why we chose this"，而不只是"what we chose"。

6 步 todo 清单：

还有一个细节值得强调：六步里有**两步是非代码工作**——第 4 步合并 specs、第 5 步写 IMPLEMENTATION.md。这是 OpenSpec 流程强制要求的：实现不只是写代码，还要维护文档状态。如果跳过，specs/ 就会滞后，IMPLEMENTATION.md 就没有，下一个人（包括三个月后的你）进这个项目，拿不到任何有价值的信息。

## [15:30 — 19:30] §四.5 implement（4 分钟）

**看实现：**

```bash
cat lesson5/project/strategies/dual_ma.py
```

约 50 行 Python，核心 10 行：

```python
ma_short = df["close"].shift(1).rolling(short_window).mean()
ma_long  = df["close"].shift(1).rolling(long_window).mean()
ma_short_prev = ma_short.shift(1)
ma_long_prev  = ma_long.shift(1)
cross_up = (ma_short > ma_long) & (ma_short_prev <= ma_long_prev)
cross_dn = (ma_short < ma_long) & (ma_short_prev >= ma_long_prev)
sig = pd.Series(np.nan, index=df.index)
sig[cross_up] = 1.0
sig[cross_dn] = 0.0
sig = sig.ffill().fillna(0).astype(int)
```

对照 specs.md 的状态表，逐行可以验证：`cross_up` 对应金叉条件（当前短均在长均上方，且前一日不是），`cross_dn` 对应死叉，`ffill().fillna(0)` 实现"其他维持上一日，初始空仓"。specs 里的每一条，在代码里都有明确的对应行——这就是"合同落地"的样子。

**现在跑自测——注意，必须用 `limit=90`，这一点很关键：**

```bash
cd lesson5/project && python -c "from strategies import dual_ma; from backtest import run_backtest; print(run_backtest(dual_ma, limit=90)['summary'])"
```

期望输出：

```
sharpe=1.1563  max_dd=-0.0938  win_rate=0.5870  cum=0.0911
BTCUSDT 在最近 90 根 K 线上的回测结果：累计上涨 9.11%，年化夏普 1.16，最大回撤 -9.38%，信号触发日胜率 58.70%。夏普 > 1 说明风险调整后收益尚可，配合曲线图可看到回撤分布，建议结合更长历史数据复跑确认稳健性。
```

现在解读一下这组数字。dual_ma 在过去 90 日累计 +9.11%，输给 lesson 4 的 buy_and_hold（+17.37%）；夏普 1.16，而 buy_and_hold 是 4.65。这看起来像是 dual_ma 失败了，但不是。

这是"**反转策略在强趋势行情里通常跑不赢简单持仓**"的经典现象。过去 90 天 BTC 总体是上涨趋势，简单持仓"无脑做多"当然赢——持仓时间 100%，行情涨就赚，没有任何空仓期。dual_ma 在死叉信号时会空仓，而强趋势行情里"及时空仓"就等于"及时割肉"，反而损失了这段上涨收益。这不是策略的 bug，是策略设计本身的权衡：双均线是反转策略，在震荡市里规避回撤的能力更强，在强趋势行情里让出部分收益。

**为什么要用 `limit=90` 而不是默认的 30？**

讲义里有一个排错表，其中第一条就是 `sharpe=0.0000 cum=0.0000`——这个问题的原因是默认 limit=30 在强趋势行情里可能全程无金叉，信号全是 0，策略等于没有开仓。90 天的数据大概率能覆盖至少一次完整的金叉死叉周期，回测结果才有统计意义。**测样本要足够大**——这是量化回测的基本原则，数据太少，结论没有说服力。

有时间的同学可以现在对比跑一下 `limit=30` 和 `limit=90`，感受一下数字差距。

| `dual_ma` | `lesson5/project/strategies/dual_ma.py` | 双均线交叉，short=7 / long=14，金叉做多，死叉空仓 |

`specs/` 与 `changes/` 的关系，可以用两句话总结：**`changes/` 是历史，`specs/` 是现在。** 每次 change 实施完都要把 specs.md 的接口段合并回 `specs/<相关文件>.md`，确保 `specs/` 始终反映"项目当前长什么样"。

这件事很容易忘——代码写完、自测通过、commit 推上去，人就走了，specs/ 没更新。三个 change 之后，`specs/strategies.md` 还在显示半年前的状态，下一个要加策略的人打开这份文件，拿不到任何有效信息，只能去翻 `changes/` 里所有变更找现状，效率极低。

解决方法很简单：**把"merge specs/"写进 tasks.md 当作必做项**——就像我们这节课 tasks.md 里的第 4 步一样，作为流程的一部分强制要求。这样实施任何 change 的人，看到 tasks.md 就会知道有这一步要做，不会漏掉。

如果你只能维护一个目录，维护 `specs/`——因为下一个人（包括下一个 AI session）第一眼看的是 `specs/`，不是 `changes/`。`changes/` 是变更日志，`specs/` 是项目当前状态的 source of truth。两者勤同步，项目文档才能真正有价值。

## [21:30 — 24:30] §五 + §六 关键认知 + 反模式（3 分钟）

快速过三条关键认知和三条反模式，每个都配一个具体场景，直接说场景，不读定义。

**关键认知一：spec 是合同。** 写 spec 的过程本身就是在逼你想清楚接口入参是什么、出参值域是什么、边界情况怎么处理。这些问题你必须回答，AI 才能照着做。vibe coding 失败的根本原因不是 AI 不够聪明，是你自己都没有把问题想清楚，结果 AI 的"猜"就成了唯一的输入——猜对了是好结果，猜错了就是 lookahead bias。

**关键认知二：rules 是底线。** UTC 时间约定写进 `.cursor/rules/strategy-conventions.mdc` 之后，Claude 每次修改 `strategies/*.py` 时都会自动看到，不需要你在每条 prompt 里重复"记得用 UTC"。Rules 的价值在于：你只需要说一次，它就永远有效。三年不改的约束，写 rules；每个 feature 一份的约束，写 spec。

**关键认知三：三层分层设计让你把精力花在刀刃上。** Rules 你写一次很少改（UTC 时间约定三年不变）；guidelines 跟着团队规范慢慢演化；spec 则是每个 feature 一份，feature 交付后归档到 `changes/`，不需要持续维护。三层叠加，不是三份重复的工作，是三个不同粒度的保障。

---

**反模式一：把 spec 写成 200 行的功能手册。**

我见过有人把 spec 写成"功能手册 + 用户故事 + 验收报告"，60 页 PDF。AI 读到 token 都炸了，真正的接口约定淹没在大量的描述里，找不出来。一个 feature 的 specs.md 通常 30-80 行就够——接口签名、行为细则、边界条件、不支持的内容，这些写完基本就是 50 行。如果你发现自己在写第 100 行，停下来问：这是在描述接口，还是在描述实现细节？实现细节属于 `design.md`，使用场景说明属于 `proposal.md`。写太多的 spec 和没有 spec 一样有害——应该拆 feature 了。

**反模式二：implement 完了不更新 specs/。**

这个上一节刚说过，再强调一遍。`specs/strategies.md` 如果永远写着"暂无策略"，那它就没有价值。同步 `specs/` 的成本很低（通常是改几行表格），但价值是让整个目录始终可信，让下一个进项目的人能靠 `specs/` 理解现状。

**反模式三：把 spec 当审计文件而不是沟通工具。**

spec 是给同事和 AI 看的"我接下来要做什么"，是沟通文档，不是合规证明。如果你写得像"本系统应当符合 ISO 标准第 X 条第 X 款，实现结果应满足行业规范"，AI 读了只会机械应付，不会帮你抓边界 case。好的 spec 用第一人称、说人话："输入行数不够时返回全 0"——这句话 AI 能直接翻译成 `if len(df) < long_window: return pd.Series(0, index=df.index)`。spec 要写到 AI 能直接执行的粒度，不是写到"合规检查员能存档"的粒度。

## [24:30 — 26:00] §七 作业 + 收束（1.5 分钟）

作业是这节课的核心练习，我认为比听课重要——动手一次抵得上看三遍讲义。

作业主题：在 `lesson5/homework/` 下选一个 feature——RSI 反转策略、MACD、布林带突破、年化收益率输出、多周期回测，任选其一或自选——按 OpenSpec 五段写一遍。30 分钟内可以完成，**不要求实现底层代码**（实现是加分项）。（实现代码若要放进项目，放在 `lesson5/project/openspec/changes/<feature-name>/` 目录。）

给你一个挑选 feature 的建议：**优先选你这周真的想加进 project/ 的东西**——这样 spec 写完你就有动力实现，而不是凑作业交了就算。作业的目的不是练格式，是练"先写合同再动手"的节奏。

作业的核心是练习从 proposal 开始，逼自己在写代码之前先把接口、边界、备选方案、任务顺序都想清楚。你会发现，写 spec 最费时的地方往往是你认为"已经想清楚"的那些细节——比如"返回值到底是 int 还是 float"、"NaN 怎么处理"、"短窗口长于 df 行数时怎么办"。这些问题你不在 spec 里解决，就留给了 AI 去猜。

提交内容：新建 `lesson5/homework/<feature-name>/` 目录，包含 `proposal.md`、`specs.md`、`design.md`、`tasks.md` 四份 markdown（`IMPLEMENTATION.md` 可选，实现代码放在 `lesson5/project/openspec/changes/<feature-name>/` 目录）。

## [26:00 — 27:00] 收束 + 铺垫 lesson 6

最后一分钟，总结和预告。

Lesson 5 我们让 AI 写了一份合同。从 proposal 到 specs 到 design 到 tasks 到 implement，五段流程走完，dual_ma 策略从一句模糊需求，变成了一份白纸黑字的接口约定，再变成了 50 行可验证的代码。Lookahead 防护是合同里写的，不是靠猜的；参数默认值有文档支撑，不是随手给的；specs/ 是现状，changes/ 是历史，两者勤同步，文档才有价值。

这节课 spec 解决了**"what"的问题**——把要做什么说清楚。

但还有另一个问题没有解决：一个完整的量化项目，单个上下文窗口装不下，你需要跨多个 session 持续推进。下一个 AI session 怎么知道你上个 session 做到哪了？怎么知道接下来要干什么？这是 **harness 的问题**——不是 spec 能解决的，而是计划管理的问题。

Lesson 6 我们用 superpowers 的 `writing-plans` + `executing-plans` 跑一个跨多个上下文窗口的多周期回测长任务。先写计划，再执行计划，计划是上下文之间的"接力棒"——每次新 session 进来，先读计划，知道上次做到哪，然后继续。这是真正让 AI 处理长任务的方式，不是靠记忆，而是靠结构。

Lesson 5 我们建好了合同，Lesson 6 我们解决"怎么持续执行"。好，这节课到这里，有问题可以现在提，或者到作业踩了坑再来讨论。
