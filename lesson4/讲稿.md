## [1:30 — 4:00] §一  Skill 是什么

第一块：Skill 是什么。

我先给你一个直觉性的类比。

你上班的工位桌上有没有贴过便签？"记得在 commit 前跑 lint""数据库连接字符串在 config.yaml 的第 38 行"——那种临时记下来备忘的小纸条。Prompt 就像这种便签：你现在要用，随手写一下，Claude 处理完，对话关掉，什么都不留下，下次还得重写。

Skill 不一样。Skill 更像你公司工位旁边的那份 SOP——"当需要审查代码变更时，按这五步走：……"。SOP 贴在那里，你不用每次开会都重念一遍，谁来干活看一眼就知道流程。Skill 就是给 Claude 的 SOP：它是一份 Markdown 文件，放进 `.claude/skills/<name>/SKILL.md` 后，Claude 每次启动都带着，触发条件匹配就调用，不触发就静默，你不需要在每次对话里重新解释。

**一句话概括：Prompt 是一次性的，Skill 是可复用的。**

讲义里有一张五行对比表，我读一下重点：

- Prompt：你打字，Claude 处理，对话结束后什么都不留下。
- Rule：自动注入上下文，比如"所有代码必须用 UTC 时间"——它是约束，不是流程。
- Subagent：你主动派遣，它跑完把结果返回来，独立上下文。
- MCP：AI 看到需要时伸手调外部工具，手缩回来继续说话，上下文连续。
- Skill：AI 看到用户意图匹配时触发，按你写的步骤来，主线对话里走。

这五个不是竞争关系，是互补的。今天要建的 backtest skill 和 lesson 3 装的 sqlite MCP 可以同时在线：skill 用来封装"如何做回测"这个流程，MCP 用来执行 SQL 查历史数据，两者协作，互不冲突。

Skill 有一个细节，值得在这里就讲清楚，因为后面会反复提：**description 这一行最关键**。Claude 不是读完整个 SKILL.md 之后再决定"要不要触发"——它是先看 frontmatter 的 description 字段，用这一行决定当前对话是否匹配，匹配了才把整个 Skill 加载进上下文。所以 description 写得越具体，Claude 触发就越准；description 写得模糊，结果是要么乱触发，要么根本不触发，你写的 Skill 等于废的。

这点我在 §三 还会专门展开，现在先记住它是"招牌"。

## [4:00 — 7:30] §二  Skill 市场速览

你不需要每个 Skill 都从零写。社区和官方已经积累了相当多现成的 Skill，可以直接装或者作为参考改写。

讲义里有张表，我念一遍，每个来源给你 30 秒定位：

**Anthropic 官方 skills**，地址 `https://github.com/anthropics/skills`，这是最权威的参考实现。想看一个"标准的 Skill 长什么样"，先去这里——官方 reference skill 的结构、description 怎么写、steps 怎么分，都可以直接抄格式。

**Superpowers**，地址 `https://github.com/obra/superpowers`，lesson 2 我们装过它。它是一套方法论框架——brainstorming、TDD、code-review——这三个用得最多。如果你做 AI 辅助开发，这三个 Skill 可以说是必备。

**ECC，Everything Claude Code**，地址 `https://github.com/affaan-m/everything-claude-code`，这是 Claude Code 的工程增强包，里面有 build、lint、代码审查、测试覆盖率这类工程类 Skill。做后端、做 CI 的同学可以重点关注。

**skill.sh**，地址 `https://skill.sh`，这是社区聚合站，按主题分类，量很大，质量参差。找常见工作流基本都能找到，搜索体验比较好。

**skillsmp**，地址 `https://skillsmp.com`，另一个聚合站，规模小一点，但垂直领域比较丰富——量化、运维、生信这些冷门垂类在这里搜比较容易找到。

选哪个，记一个心法：

- 找标准参考实现，看官方；
- 找工作流——brainstorming、TDD、code-review——找 Superpowers；
- 找代码审查、build、lint 类工程 Skill，找 ECC；
- 找冷门垂类，去 skill.sh 或 skillsmp 搜。

## [7:30 — 11:30] §三  Skill 文件结构

来看 Skill 文件的结构。

一个最小的 SKILL.md 长这样：YAML frontmatter + 标题 + 若干 Markdown 节，其中关键节包括"何时触发"、"输入约定"、"步骤"、"反模式"和"示例"。

frontmatter 里两个字段：`name` 是 snake\_case 的标识符，`description` 是触发说明。

我重点讲 description，因为这是 Skill 能不能跑起来的命门。

给你两个对比例子，这两个例子讲义里也有，先听我念一遍：

第一种写法：`"代码审查工具"` ——这是错的。太宽泛，"代码审查"是什么？什么时候触发？输入是什么？Claude 不知道，它会在不该触发的时候触发，或者根本不触发。

第二种写法：`"当用户给出一段 git diff 并要求 review 时使用——输出风险列表 + 每条风险的严重等级（P0/P1/P2）"` ——这才对。它告诉 Claude：输入是 git diff，触发条件是"用户要求 review"，输出是带严重等级的风险列表。三件事都说清楚了，Claude 可以准确判断。

同样的逻辑，我们的 backtest skill 的 description 写的是：当用户描述一个交易策略、要求回测时触发，把策略翻译成 Python callable，调 `run_backtest`，解读结果。动词、输入、输出、触发时机，全在这一行里。

步骤段怎么写——把整个流程拆成 5 到 7 步，每步一两句话描述一个动作。步骤要具体到 Claude 知道"干什么"，但不要长到变成文档。底层实现细节放进 Python 代码里，SKILL.md 里只写"调哪个函数、传什么参数、拿什么结果"。

有个原则很重要：**SKILL.md 是说明书，不是实现**。它告诉 Claude 什么时候用这个工具、怎么用、用完怎么解读结果——底层引擎（我们这里是 `backtest.py`）是 Python，SKILL.md 不负责运行任何代码，只负责告诉 Claude"下一步你该干什么"。两者分离，各自可以独立演进：你改了 `backtest.py` 的指标计算逻辑，SKILL.md 可以完全不动；你改了 SKILL.md 的步骤顺序，`backtest.py` 也不需要变。

## [11:30 — 17:00] §四  动手做：写 backtest skill

这一节是 lesson 4 的核心。我们不是从零写这些文件——仓库里已经备好了——我们逐个看一遍，理解它们怎么协作。

整个 backtest skill 由三个文件组成：`lesson4/project/backtest.py`、`lesson4/project/.claude/skills/backtest/SKILL.md`、`lesson4/project/.claude/skills/backtest/example_strategies.py`。三块拼图，缺一不可。

**步骤 1，看 `lesson4/project/backtest.py`。**

```bash
head -50 lesson4/project/backtest.py
```

这是底层引擎。它干的事情很清楚：从 `prices.db` 的 `ohlc` 表读 K 线，接受一个策略 callable，计算夏普、最大回撤、胜率、累计收益，画一条累计收益曲线写到 `cum_BTCUSDT.png`，生成一段中文 summary，最后返回 dict。

有两个设计决策值得讲一下。

第一，**策略 callable 是参数，不是硬编码**。`run_backtest(strategy_func, symbol=...)` 接受任意符合约定签名的函数——`def strategy(df) -> pd.Series`，返回 +1/0/-1 信号。引擎不知道策略的逻辑，策略不知道引擎的实现，两者解耦。这让 Skill 可以接受任意新策略：用户描述一个新策略，Claude 把它翻译成符合签名的 callable，直接传进去跑，引擎不需要改。

第二，**`signal.shift(1)`**。今天的信号基于昨天的价格——不能用今天的收盘价去决定今天的开盘信号，这是真实量化回测里最常见的 bug，叫 lookahead bias，也叫未来数据偷看。如果你在信号里用了今天的数据，回测结果会虚高，因为实盘里你根本没机会在当天收盘前知道收盘价。`backtest.py` 里用 `signal.shift(1)` 解决了这个问题：把信号往后移一格，确保今天执行的是昨天决定的信号。

**步骤 2，看 `lesson4/project/.claude/skills/backtest/SKILL.md`。**

```bash
cat lesson4/project/.claude/skills/backtest/SKILL.md
```

看三处。

第一处，frontmatter 的 description——按我们刚才说的标准，它写明了触发时机（用户描述交易策略并要求回测）、做什么（翻译为 callable、调 `run_backtest`、解读结果）、不做什么（不替用户优化策略）。这三件事都在一行里。

第二处，步骤段——"用户自然语言策略 → Python callable → `run_backtest` → 解读结果"，拆成 5 步，每步一句话。Claude 读到这里不需要猜，直接按步骤来。

第三处，反模式段——明确告诉 Claude 不要做什么：不替用户优化策略（那是用户的事）、不引入 lookahead bias（哪怕用户没提）、不忘告诉用户 PNG 路径（图生成了但用户不知道在哪，等于白生成）。反模式段是很多 Skill 忘掉的，但它非常有价值，因为它是在帮 Claude 避开"合理但错误"的行为。

**步骤 3，看 `lesson4/project/.claude/skills/backtest/example_strategies.py`。**

```bash
cat lesson4/project/.claude/skills/backtest/example_strategies.py
```

两个起手模板：`buy_and_hold`——始终满仓做多，基线对照；`ma_crossover_7`——收盘价高于 7 日均线时做多，否则空仓，最简单的趋势跟踪示例。

这个文件的作用是双重的：一方面帮 Claude 看"策略 callable 长什么样"——用 rolling、fillna 处理 NaN、返回 +1/0/-1，有了具体例子 Claude 翻译新策略时不会出格式错；另一方面也帮学员——你下次要加一个新策略，照着这两个写，不会踩信号格式的坑。

**步骤 4，直接跑一次。**

```bash
cd lesson4/project && python backtest.py
```

先在 Python 层验证引擎能跑，不通过 Skill，就是直接调 Python。期望看到一段中文 summary 打印到终端——夏普、最大回撤、胜率、累计收益——同时 `lesson4/project/cum_BTCUSDT.png` 应当生成。

讲义排错表快速过一下：缺库的装 `pip install pandas numpy matplotlib`；`ValueError: prices.db 没有 BTCUSDT 的数据` 是忘跑 `seed_db.py`，补跑一下；PNG 没生成，多半是 `backtest.py` 里 `matplotlib.use("Agg")` 放错了位置，要在 `import matplotlib.pyplot` 之前；`sqlite3.OperationalError: no such table: ohlc` 是 `prices.db` 是空文件，`rm lesson4/project/prices.db && python seed_db.py` 重建。

## [17:00 — 21:00] §五  动手做：用 skill 跑两个策略对比

引擎验证通了，进入最有意思的部分——让 Skill 真正工作起来。

确认在 `lesson4/project/` 目录，启动 Claude Code：

```bash
cd lesson4/project && claude
```

在对话框里整段粘贴这条 prompt：

```
用 backtest skill 评估两个 BTC 策略：
1. buy_and_hold（始终满仓做多）
2. ma_crossover_7（close 高于 7 日均线时做多，否则空仓）

各 30 天日 K 线（symbol=BTCUSDT, interval=1d, limit=30），给我对比报告。
```

注意这条 prompt 里没有任何 Python 代码，没有告诉 Claude 怎么实现策略，没有解释 `run_backtest` 是什么，只有两个策略的自然语言描述和参数。

粘贴之后，观察 Claude 怎么应对。

它会先识别出"用 backtest skill"这个触发意图，加载 `SKILL.md`，然后按步骤走：把 `buy_and_hold` 和 `ma_crossover_7` 翻译成符合约定签名的 Python callable，调 `run_backtest`，把返回的 dict 解读成对比报告。

期望看到的对话大概是这样——讲义里有完整示例：

两次 Skill 调用，各自返回 sharpe / max\_drawdown / win\_rate / cumulative\_return / rows / png\_path，然后是一段 150-200 字的中文对比。

结果解读我多说两句，因为这里有教学点。

buy\_and\_hold 累计收益 17.37%，ma\_crossover\_7 是 4.51%，领先超过 12 个百分点。夏普比 4.65 对 2.28，风险调整后也是 buy\_and\_hold 赢很多。两个策略的最大回撤相同，都是 -4.24%，说明回撤风险这个窗口内没有明显差异。

这结果合理吗？非常合理。过去 30 天 BTC 一路涨，简单持仓当然赢。ma\_crossover\_7 是趋势跟踪策略，它会在价格跌破均线时减仓，但单边上涨行情里"及时空仓"反而是在损失收益，所以它落后 buy\_and\_hold 很多。

换一段震荡行情，结果会反过来——ma\_crossover\_7 在震荡中靠均线信号能规避部分下跌，buy\_and\_hold 则要全程承受波动。

这就是为什么单一窗口的回测意义有限。同一个策略，换个时间段，结论可能完全相反。Lesson 5 以后我们会做多周期验证，这个话题会继续。

现在我们观察三件事，讲义里也列出来了：

第一，**Claude 自己把策略名翻译成了 Python callable**——你没写任何 Python，它参考 `example_strategies.py` 里的写法，自己实现了符合约定签名的函数。这是 Skill 的核心价值：你提供了模板，Claude 直接复用，而不是从零猜格式。

第二，主线对话里只有两次 Skill 调用 + 一段对比文字，**没有把 `backtest.py` 的代码原文 dump 出来**。用了最小的"出口"：把能力封装好，Claude 只消费接口，不关心实现。

第三，**复用而非重写**——下次你要测新策略，prompt 里直接说"用 backtest skill 评估……"即可，不需要重新解释流程，不需要告诉 Claude `run_backtest` 在哪、签名是什么、怎么处理返回值。你只需要说新策略是什么，Skill 负责剩下的。

关于数字：讲义里说明过，sharpe / cumulative\_return 这些是课件制作日的行情跑出来的，你跑的时候行情已变，数字会不同，这是正常的。重要的是流程走通、各指标有值。

## [21:00 — 22:30] §六  关键认知

我想把 MCP 和 Skill 的关系再说一遍，因为到这里你已经两个都体验过了，值得放在一起对比。

MCP（lesson 3）让 AI **消费**外部接口——sqlite MCP 给了 Claude "执行 SQL" 这个能力，Claude 按需调用，不调用时安静。你作为使用者，配好连接就够了，不需要定义"怎么查"这个流程。

Skill（lesson 4）让你给 AI **生产**接口——你把"如何回测一个策略"的完整流程写进 `SKILL.md`，Claude 看到用户意图就执行，不需要你每次解释。你作为设计者，定义的是"流程"，不是"外部连接"。

两者互补，不冲突。MCP 负责连接外部系统，Skill 负责封装可复用流程。前者扩展能力边界，后者提升执行一致性。

还有一个实用判断法则——什么时候该把一件事做成 Skill？

不需要等到"我感觉这件事应该封装了"。有一个简单的阈值：**当一件事你做过 3 次以上，且每次流程基本不变，就值得考虑做成 Skill**。代码审查、生成 release notes、分析日志、回测策略——这类高频且结构固定的任务，都是好的 Skill 候选。你做了 5 次以上还在每次重新解释流程，是在浪费时间。

做成 Skill 之后，不只是你自己省事——你写的 SKILL.md 也可以分享给团队，让团队里每个人都能用标准流程调 Claude 做同一件事，结果的一致性会好很多。这是 Skill 相比 Prompt 的另一个优势：可以版本化、可以团队共享、可以持续改进。

## [22:30 — 23:30] §七  反模式

三条反模式，快速过，每条一句话主旨 + 一个具体场景。

**第一条：SKILL.md 写得太长（500 行手册）。**

SKILL.md 是触发说明书，不是文档库。如果你把"所有可能情况"全写进去，Claude 读到一半就搞混了，触发时也会犹豫不定。保持步骤在 3 到 7 条，每条一句话描述动作。底层实现细节放进 Python 代码里，SKILL.md 只写"调哪个函数、传什么参数、拿什么结果"。我见过有人把整个策略回测的数学公式都写进了 SKILL.md，结果 Claude 在"理解公式"上花了大量上下文，实际执行的步骤却出了岔子。精简胜于全面。

**第二条：让 Skill 决定业务规则。**

Skill 是流程封装，不是决策中心。"什么样的夏普比算好策略"是业务判断，应当在 Rule 或 prompt 里告诉 Claude，不应该硬写进 SKILL.md。比如 review skill 不该在文件里写死"100 行以内是好代码"——那是团队规范的事，而且团队规范会变。Skill 只管"拿到 diff → 找风险 → 输出列表"，评判标准由你在对话里给，或者在 Rule 里定义。Skill 是流程，不是政策。

**第三条：SKILL.md 内嵌密钥或私有路径。**

SKILL.md 是文本文件，会 commit 进仓库，也会在每次会话里被 Claude 读到。任何 API key、access token、内网 IP、私有路径都不要硬编码在里面。正确做法：密钥通过环境变量（`os.getenv("MY_KEY")`）或 `.env` 文件注入，SKILL.md 里只写变量名，不写值。这条听起来像常识，但我见过的 Skill 泄漏事故里，有相当一部分就是开发者"临时测试"时把 key 硬编码进了 SKILL.md，然后忘记删，推进了仓库。别侥幸，写文件之前先想清楚：这行内容如果出现在 GitHub 上，我能接受吗？

## [23:30 — 24:30] §八  作业 + 收束

作业主题很清楚：**从日常工作里挑一个高频任务，设计成 SKILL.md**。

不要求实现（有加分项）。我们要求三样东西：三句话说明这个 Skill 的用途、触发条件、输入输出；按 §三 的格式写出完整 SKILL.md，参考 `lesson4/project/.claude/skills/backtest/SKILL.md` 的写法；可选加分项是把 SKILL.md 装进 `.claude/skills/<name>/SKILL.md`，实际在 Claude Code 里跑一次，提交对话截图。

几个常见的高频任务，适合拿来练手：代码审查（输入 git diff，输出风险列表）、日志分析（输入错误日志段落，输出根因分类）、接口文档生成（输入函数签名，输出 OpenAPI 格式描述）。选你自己最熟悉、最常做的那类，因为你最了解"这件事什么步骤最关键"、"最容易出什么错"，这些都是好 SKILL.md 里的内容。

作业重点是 description 写得能让 Claude 准确触发——这是整节课的核心技能。description 写得具体，Skill 才能工作；description 写得模糊，再好的步骤段也没用。
